# 调度程序的坑

都是实际踩过的。每条写：现象、原因、对策。

| # | 现象 | 原因 | 对策 |
|---|---|---|---|
| 1 | worker 早就交付了，调度程序却一直显示“在跑”，好几个小时不结束 | worker 在后台启动的本地服务器、headless 浏览器继承了调度程序的输出管道；只要它们还活着，管道就不关，调度程序永远等不到结束 | 输出写到文件而不是管道；每个 worker 用独立会话（进程组）启动，结束后清理整组进程；任务说明里也要求 worker 自己关掉服务 |
| 2 | 一批任务在同一时刻全部失败，之后每次重试都在几十秒内失败，6 次机会很快耗光 | 模型接口整体断连，持续了几十分钟到一小时；重试间隔太短，每次都撞在断连里 | 重试间隔递增（例如 5 分钟起步、逐次加长）；重开前先单条探测；断连期间不要盲目重开 |
| 3 | 某个任务被直接跳过，没有再跑 | 上一轮失败时把 worker 的半句回复（“接下来我做……”）写进了“已完成”标记文件，下一轮按“标记存在 = 已完成”跳过了它 | 只有成功才写已完成标记 |
| 4 | 任务显示“成功”，但交付物里没有报告 | 回退逻辑在报告缺失时读到了目录里原有的模板文件（例如复制原型时带过来的旧设计文档），字数达标就判了成功 | 核验时比对文件时间戳和大小；复制原型时删掉旧报告，或把旧文档改名；回退只认本轮新写的文件 |
| 5 | 一启动就全部报“缺凭据” | 工具把 API key 从配置文件迁移进了自己的凭据服务，无界面模式读不到 | 开跑前单条探测；把 key 放进只有本人可读的环境文件，由决策者自己写入，调度程序启动前加载，绝不打印 |
| 6 | worker 的最终回复只有一句“接下来我做……” | 长任务中途被打断，最后一条消息不是总结 | 以 worker 写下的报告文件为准；要求边做边写盘 |
| 7 | 原型截图看起来对，实际页面却是白的或还在加载 | 截图在模型加载或主题过渡完成前截下；或者预览面板隐藏时页面的动画帧被暂停 | 截图前等加载完成的信号；必要时用独立的 headless 浏览器截图；核验时读页面上的实际数值，不只看图 |
| 8 | 并行稿子合并时冲突 | 几份稿子各自给新接口分配了同一个编号，或者各自修订了同一个公共对象模型 | 合并前统一编号，把所有公共模型的修订汇总成一份清单再合入 |
| 9 | 推送大仓库时连接被远端断开 | SSH 推送大包时被代理或远端掐断 | 改用 HTTPS 加代理推送，必要时用 HTTP/1.1 |
| 10 | 在错误的目录里启动了调度程序，立刻退出 | 后台命令的工作目录和预期不同 | 启动命令里显式 `cd` 到任务目录，启动后检查进程数和运行记录 |

## 一个最小可用的调度程序应当做到

- 读任务列表（每个任务：编号、工作目录、任务说明）。
- 每个任务一个独立进程组，输出写文件，有总时长上限。
- 交付判定：以约定的报告文件为准，检查开头格式与长度；**只有成功才写已完成标记**。
- 失败重试带递增等待；续跑时在任务说明后追加“检查已有产物、在此基础上继续”。
- 每次尝试追加一条运行记录（编号、第几次、是否成功、耗时、字数）。
- 并发上限可配。
