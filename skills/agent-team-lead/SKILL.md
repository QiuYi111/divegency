# 当总指挥

目标：让一批 worker 的产出**拼得起来、经得起核验、由决策者拍板**。并行越多，瓶颈越不在写，而在三处：**接口不稳（拼不起来）、核验跟不上（审不过来）、算力和模型接口撑不住（跑不完）**。这份 skill 的全部规则都是为了这三处。

和 [`divergent-research`](../divergent-research/SKILL.md) 的分工：那一份管“怎样独立探索、去重、验证、选择”的研究纪律；这一份管“怎样组织很多 worker 把一个大项目做完”的执行纪律。赛跑和筛查时，两份一起用。

## 0. 角色

- **总指挥（你）**：拆任务、写任务说明、开跑、核验、整合、对决策者汇报。**不把核验外包给 worker，也不替决策者拍板。**
- **worker**：在**自己的目录**里完成一张任务单，产出文件。worker 在单个任务内通常可靠，但**跨模块的结论容易说过头**，所以凡是要进主线的结论都由总指挥核验。
- **决策者（人）**：只看结论、体验原型、勾选审核表。时间稀缺，交给他的东西要短、要能直接选。

## 1. 先选工作类型

| 类型 | 什么时候用 | 每路产出 | 总指挥做什么 |
|---|---|---|---|
| **赛跑** | 方向有真实的方案之争 | 立场一句话 + 设计文档 + **可运行原型** + 截图 + 补充考题 + 报告 | 体验、比较；通常推荐**分层组合**而不是二选一（见第 4 节） |
| **起草** | 方向明确，只缺把它写成规范文档 | 设计节点 + 考题补充 + 报告 | 逐份核对依据、一致性、与已有决定的冲突 |
| **筛查** | 怀疑有“需求写了、设计没接”的盲点 | 盲点清单：证据、在哪里搜过没找到、严重度、补法 | 去重归并、抽查原文、分级 |
| **研究** | 需要外部证据或成熟实现选型 | 证据表：来源、原文短引、核实状态、反面证据 | 抽查原文与数字（按 `divergent-research` 第 3.5 节） |
| **合并** | 决策者选了组合方案 | 一个规范节点 + 合并裁决记录 | 检查裁决是否符合决定 |
| **反思** | 出现了强参照物（竞品、开源项目） | 论点表：对方证据、己方证据、建议（保持 / 改 / 删 / 加） | 综合多份反思，**先给判断再动设计** |

一个大阶段常见的节奏：**筛查 → 赛跑 / 起草 → 决策者拍板 → 合并 → 再筛查一轮**，直到会改接口的盲点清零，再进实现。

## 2. 写任务说明

模板见 [任务说明模板](references/brief-template.md)。每份都包含五块：

1. **你是谁、做什么**：一句话角色 + 一句话目标。赛跑写清“你和另外几人各持一种立场，由决策者挑选”。
2. **立场或范围**：赛跑给每路**一种互相不同的立场**（换权威、换求解路线、换中心视图），不是同一方案的几个版本；筛查给每路**一个视角**。
3. **必读（只读）**：写**绝对路径**，列需求、已有决定、相关设计、考题、格式范例、前人产物。worker 不需要全库扫描，只读这些。
4. **硬约束**：每份都带上项目的不可协商规则。常用的几条：
   - 每个设计元素必须对应一条需求或明显的体验改善，否则不做；
   - 成熟实现优先，写库名、版本、许可证，不手搓；
   - 复用已有机制，不另造平行体系；
   - 会进接口的内容给出 schema 草案。
5. **交付与运行**：交付哪些文件、文件名、第一行格式；**边做边写盘**；做不到的**如实写**；本地服务和浏览器用指定端口范围，用完自己关掉；依赖和缓存放在自己目录里。

续跑时在原说明后面加一段：“上一轮因接口中断停止，不是你的问题；先检查已有产物，在此基础上继续，不要从头重写。”

## 3. 开跑与调度程序

一张任务单 = 一个独立目录 + 一个 worker 进程。参考实现见 [`scripts/race_runner.py`](scripts/race_runner.py)，工程坑见 [调度程序的坑](references/runner-pitfalls.md)。必须做到：

- **开跑前先单条探测**：发一句“回复 ok”，确认凭据和接口可用。凭据可能被工具悄悄迁移。
- **输出写文件，不走管道**：worker 在后台留下的本地服务器或浏览器会继承管道，调度程序就永远等不到结束。每个 worker 放在独立会话（进程组）里，结束时清理整组进程。
- **重试要有递增等待**：接口断连可能持续几十分钟，重试间隔太短会把机会全部耗光。
- **只有成功才写“已完成”标记**：失败时留下的半句话不能让下一轮把任务当成已完成而跳过。
- **以交付文件为准**：worker 的最后一句回复常常只是“接下来我做……”，以它写下的报告文件为准；同时警惕**假成功**（例如报告缺失，回退读到的是目录里原有的模板文件）。
- **并发按接口承受力定**，先 25，再按压测提高；所有任务的状态都写进一份可追加的运行记录，换一个总指挥会话也能接手。

## 4. 核验（不能外包）

worker 交付后，总指挥逐份做：

1. **完整性**：该有的文件都有吗？时间戳是这一轮的吗？有没有“报告缺失、回退读到旧文件”的假成功？
2. **抽查原文**：每份研究或盲点清单，至少抽 2–3 条最承重的论断，打开原始来源核对原话和数字。核过的写进汇总，没核的标“未核实”。
3. **亲手重跑**：原型的自动测试自己再跑一遍；看截图，必要时自己截图。“测试通过”要你亲眼看到。
4. **跨稿冲突**：并行起草时，常见几份稿子各自占用同一个编号（接口号、节点号），或者各自修订同一个公共模型。合并前统一编号，把所有公共模型的修订汇成一份清单。
5. **与已有决定的冲突**：稿子与已批准的决定冲突时，以决定为准并在合并记录里写明；如果决定本身看起来错了，写进审核表请决策者重新拍板，不要悄悄改。

**赛跑的推荐通常是分层组合**：几条立场往往证明的是同一问题的不同层（权威表示、求解后端、分析或高保真层），各取被实测证实的部分。只有真互斥时才二选一。

## 5. 对决策者

- **审核表**：写成决策者能直接勾选的文件（例如 Obsidian 里的复选框）。模板见 [审核表模板](references/review-sheet-template.md)。
  - 先给结论和推荐；
  - 每个方案一行：亮点、不足、证明了什么；
  - “请决定”一节只放需要他拍板的事，推荐项放第一个。
- **体验先于阅读**：有原型就先给可点开的地址和“先看哪里”，决策者体验完再勾。
- **决定落成记录**：勾选后写成正式的决定记录（编号、依据、后果），并在审核表末尾追加“结果”一节。决策者的口头更正（例如“viewer 太怪，以后换成熟实现”）也写进决定的后果里。
- **没勾的不动**；勾选与口头指示冲突时，先问。
- **坏消息直说**：例如“承诺补入的 76 条里没有一条完整落地”，这种发现放在最前面。

## 6. 节奏与汇报

- 决策者问“如何了”时，汇报：**完成了什么、卡在哪里、原因、已经做了什么补救、下一步**。不要把调度细节堆给他。
- 后台任务跑着时可以并行做核验或整合，但**不要预测或编造未完成任务的结果**。
- 出现强反思意见（例如“三分之一的复杂度是过度设计”）时，先停住相关的整合，等同批反思全部交付，再给综合判断。

## 交付前自检

①每份进主线的产物都核过原文或重跑过吗？②有没有假成功、旧模板冒充新报告？③并行稿子的编号和公共模型修订统一了吗？④推荐与已有决定冲突的地方，是写进审核表了，还是悄悄改了？⑤审核表的“请决定”是否只剩需要拍板的事？⑥决定是否已落成记录、审核表是否追加了结果？
