# 实验与独立评测

这份约定只在需要做真实实验、代码或硬件验证时读取。事实调研、轻量方案比较不必套用。

## 1. 先锁定比较依据

1. 保存用户原目标、必须满足的约束，以及可以推翻某个方案的反例。
2. 对现有系统复现基线：同一版代码、数据、硬件、随机种子和计算预算，记录真实原始结果。基线不能复现时先修复或说明不可比。
3. 在候选实验之前锁定指标、方向（越大越好或越小越好）、运行次数、算力和时间上限。
4. 估分辨率：同一基线重复测出波动带，把能分辨的最小差距写成 **MDD**。两个候选差距小于 MDD 时判并列，不得宣称“最佳”，也不得据此把预算全转给其中一条。
5. 如有条件，把验证集与最终测试集分开。实验 Agent 只能根据验证集调方案；最终测试集由独立评测方保管、执行。
6. 机械／硬件工程用没有参与设计调试的工况或样件作为保留测试；没有单独测试样件时说明原因和证据局限。

## 2. 不要让工作退化为无尽微调

- 把候选分成“稳妥、便宜、可迅速否定”和“不同原理、失败风险高、潜在收益大”两组。必要时两组同时推进；不要把绝大多数预算全耗在第一组。
- **先登记，再运行**。每个关键实验写清：改变了什么、假设（“若 X，则 Y，因为 Z”）、支持它的原始资料、成功指标、预计时间与资源、为何属于原理改变而非普通调参。无法解释最后一项的，降为常规优化。
- **先写死双向预言**：登记时写“若假设成立，指标应落在 ___；若不成立，应落在 ___；两者可区分的最小差值 ___”。运行后把实测值与预言**并排**保留，不得回改预言。预言与实测不符却仍宣称支持假设的，必须给出新的可再检验解释，并标“事后解释”。
- 实验日志记录代码版本、输入、环境、命令、耗时、资源、结果与失败原因。先做短时间、真实输入的冒烟测试，再决定是否投入完整预算。
- 超过约 5 分钟、需要付费算力或外部设备，就按“较贵实验”处理：先按本节锁定预算与分辨率，再做冒烟测试。
- 多个实验并行时避免超额申请 CPU／GPU／设备；跟踪排队、空闲、超时和冲突，停止长期无进展的任务。
- 长任务在**阶段切换**（一组实验结束、准备选型、写终稿）重新判断：是否只有调参？能否从问题的物理或数学约束出发换一种问题描述或机制？有没有没看过的原始研究？宿主有定时能力时再叠 60 分钟提醒；没有就不要依赖定时。
- 结果好时不要把剩余预算全投该路线；保留一次探索其他机制的机会。
- **失败先分类**：资源不足、崩溃、数值异常、实现错误，先修复再测；核心假设合理但路径不通，尝试转向；只有反例击中核心假设，才舍弃整条路线。保留失败证据，不能把一次程序报错说成原理失败。

## 3. 结果交给别人复核

- **“已验证”三项齐全**：可重跑（命令、输入、版本、原始输出位置）；会失败（给出一个若结论错就会失败的输入，并说明为何能区分）；判定者没参与提出且带来新东西（新资料、新输入、重跑）。缺一项只能写“未验证”。
- 措辞随等级：独立执行且可重跑→“在保留集上优于基线”；自测→“开发集结果，尚未独立验证”；无测试→“未验证”。不得越级。
- 优先让独立评测者运行**冻结**的程序与指标，记录 commit 或快照校验值。实验 Agent 不得读取最终隐藏数据，更不能根据隐藏成绩继续选型。评测进行时不改被测版本；收到问题后修改，就应重新冻结并接受新的未知测试。
- 审查完整记录、代码差异、分组和指标，重点查：只报告有利子集、用测试集调参、修改评分办法、硬编码结果、忽略运行失败、改变时间／算力预算。
- 显示各次原始结果与波动，不只给最佳一次；验证集分数和独立测试分数分开标注。
- 外部验证不能开展时，写“开发集结果／尚未独立验证”，不得写“已证明优于基线”。

## 4. 停止或继续

当不同机制的候选都经过最低成本的反例测试、额外实验不能带来足够新信息，或资源上限达到时停止。留下可复查的最佳方案、不同路线、失败日志和下一步最有信息量的实验。

## 5. 研究对象是 Agent／Skill 本身时

不要只用“让 Skill 改进自己”判断效果。它容易让执行者提前知道缺陷，又自己制定及检查答案。

拿**未参与设计的真实任务**比较四组：A 单 Agent 深度研究；B 多个 Agent 收同一目标、不指定方向；C 多个 Agent 收中性共同任务书和不同宽泛方向；D 在 C 的总预算内留出一部分做独立复核。尽量使用同一个模型、工具与总 Token／搜索预算，同时另记实际耗时。

事前确定三项指标：外部复核后仍成立的**不同原理数**、最佳方案在独立测试上的表现、每得到一个有效新方案的耗时与 Token。让看不到 A／B／C／D 标签的人审查；真实工况、隐藏测试或原始资料对照优于模型主观打分。记录共同任务书原文，核查有无将答案、疑似缺陷或具体检验题泄露给各路。

如果只是新旧版本互相自测、不同组预算不一致，或没有真正完成所有分路，就只报告“可执行性／已知问题回归”，**不报告能力提升百分比**。
