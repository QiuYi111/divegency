# 分路研究

目标：在给定时间和工具预算内，找出**更多有依据、原理真正不同、能够检验**的答案或方案。不要把“多个 Agent 分头写报告”误当成多路探索。

## 先确定任务

1. 把用户的**最终目标原文**、硬约束、可用资源和禁止事项写成一份共同任务书。区分四种用途：`facts`（查清事实）、`decision`（现有方案选型）、`design`（设计新方案）、`algorithm`（研究或改进算法）。任务可以混合；按最终交付物选主模式。
2. **在看到候选结果前**，写下什么算成功、哪些条件一票否决、什么证据会推翻结论。只限定结果，不预先指定实现方式。
3. 从原始资料入手：论文正文与附录、代码及测试、标准原文、官方手册、原始数据、实物测量或用户提供的工程文件。二手文章用于发现线索，不直接当最终依据。
4. 给任务定预算：`quick`：首轮 3 个研究 Agent、最多 1 个补充；`standard`（默认）：首轮 4 个、最多 2 个补充；`deep`：首轮 6 个、最多 4 个补充。小问题或用户明确不要并行时，减少调度；用户明确要求并行时至少尝试 3 路。不要为了凑数无条件增加 Agent。
5. 对要改进的现有系统、实验或算法，先确认**可重复的基线**和固定的衡量方法；没有可靠基线时，先说明缺口，不能用无法比较的数字竞选。

## 1. 生成不同的大方向

根据目标的不同因果解释、可用信息、数学描述、约束瓶颈、相邻领域类比，提出互补的**起始视角**。先花少量搜索确认领域版图，但避免被第一批热门方案锁定。

- 每个视角应能**独立解决整个目标**，不是一段报告任务。
- 视角是一句开放问题或研究范围；**不能**规定算法、产品、论文、工具或预期结论。
- 别机械套用“研究员／工程师／反对者”这类固定人物。不同任务应产生不同视角。
- 尽可能留一名不附带视角的 Agent，作为发现意外路线的对照；`quick` 下至少留一条跨领域或自由探索路线。
- 检查方向之间是否只换了说法；如果是，重新划分。允许 Agent 发现更有价值的方向后偏离起始视角。
- 尽量覆盖本领域的原始研究和其他领域可借用的原理，尤其留意从任务本身的物理、数学或业务规律出发的办法，不要只在现有工具之间选择。

例如“提高工程图转三维模型的成功率”，可从几何约束、视觉重建、程序搜索、其他逆问题开始；但**不得**写成“用某个网络／论文／求解器”。

## 2. 真正独立的首轮研究

优先使用宿主提供的原生子 Agent／并行委派功能。每个 Agent 获得：

1. **完全相同的共同任务书**（包括成功标准与硬约束）。
2. **仅属于自己的**一个宽泛视角；自由探索 Agent 则不附加视角。
3. 同一份 [独立研究交付要求](references/agent-contract.md)。

严禁给 Agent 发送主 Agent 偏好的候选答案、其他 Agent 的计划或已得出的结论。首轮结束前不互相讨论；每个 Agent 独立检索、推理、提出**完整答案／完整方案**，记录最原始的资料及失败的探索。

若宿主不提供真实隔离的子 Agent：使用可用的独立新会话；仍不支持时，明确写出“单 Agent 模拟，独立性未验证”，**不得**假称完成多 Agent 研究。

保存首轮原始产物，按 Agent 分开存储（例如 `tracks/D1.md`），不以最终摘要替代原始记录。不要要求所有 Agent 使用相同的搜索路线、预设步骤或技术栈。

## 3. 建立方案库，找出遗漏

等首轮 Agent 都交付后，再进行汇总。不要先选赢家。

1. 逐个提取候选的核心原理、输入信息、关键假设、适用边界、原始证据、可测结果；事实研究则提取各自**完整结论与证据链**。
2. 比较**为什么有效**，而不是名字、措辞或所属领域。相同机制的表面变体归为同一族；不同机制、不同关键假设或失败边界的方案应分别保留。
3. 保留有前途的不同路线，也保留有价值的失败路线及其反例。区分**常规优化**（调参数、换同类工具）与**原理改变**（换问题描述、信息来源、目标或机制），不要把常规优化冒充新发现，也不要让一个高分常规答案挤掉所有不同方案。
4. 识别四类空白：没人探索的机制；证据缺失；彼此矛盾的发现；有潜力但验证不足的路线。
5. **只在有价值时**派第二轮 Agent：给新的宽泛起始方向，仍要求独立解决完整目标；或单独派验证 Agent 核查争议。不要把第二轮全部用来润色第一轮的赢家。
6. 长任务每完成一轮重要实验或约每 60 分钟复查一次：最近是否只围绕当前最好方案微调？是否仍有未测试的不同原理？是否有任务资源闲置或实验互相抢占？下一笔时间和算力是否应该转给更有信息量的路线？据此暂停、结束或另开方向，勿让一轮好结果锁死后续探索。宿主没有定时提醒能力时，在每次阶段切换时主动检查。

如需保存可机读的方案库，用 [portfolio.json 约定](references/portfolio-format.md)。运行 `python scripts/check_portfolio.py <portfolio.json>` 检查引用、空白方向、重复机制标识、验证记录。脚本只检查记录一致性；**不能代替**语义去重和科学判断。

## 4. 验证，然后选择

- 先执行硬约束，再对比效果、成本、复杂度、鲁棒性和风险。评价维度必须与任务目标相关；不要凭一个随意加权的总分决定胜者。
- **事实调研**：逐条打开原始来源、核对引用和时间，主动寻找反证；标明证实、冲突、暂不可证。
- **方案选型**：查规格、限制、价格与维护等一手资料；对关键争议做可重复的小试用。
- **工程设计／算法改进**：允许时编写最小原型；使用同一输入、同一预算、同一指标和反例。保留命令、版本、原始输出与失败记录。把高风险但可能改变原理的实验与稳妥的局部改进**分别安排**，不要把所有预算用在调参数。处理较长或昂贵的实验时，先读 [实验与独立评测](references/experiment-protocol.md)。未经允许，不修改生产系统或使用昂贵资源。
- **评测必须独立**：尽量让方案提出者看不到最终保留的测试数据或隐藏案例，固定评价代码与指标，由独立执行者复测。另核查是否选择性报结果、使用了测试信息、擅改指标或硬编码答案。不能做到隔离时，明确报告验证强度不足。
- 先让独立的审查 Agent 找每条路线的致命缺陷，再根据外部证据或实验做决定。模型评分仅用于分配调查精力，不等于验证。
- 如果没有明显赢家，给出几条互不支配的路线及其适用条件；不得强行宣称“最佳”。

## 5. 最终交付

先给结论，再给可复查的依据：

1. **推荐什么、为什么、在什么条件下会改选其他路线**。
2. 每条主要路线的核心原理、优势、失败条件与关键原始资料。
3. 本次覆盖了哪些搜索方向、哪些没有覆盖、多少条真正不同且达到证据门槛的路线；不能用 Agent 数或搜索结果数充当多样性。
4. 哪些结论已实测、哪些仅有资料支持、哪些仍是假设；给出复现方法或下一次最有价值的测试。
5. 附上未被采纳路线与舍弃理由，允许用户据此重新开一轮探索。

在发现新增可行机制很少、关键空白已解释、预定预算耗尽或用户要求停止时收尾。未完成项要说清楚，不无限追加搜索。

## 来源与维护

设计借鉴了 STORM 的视角发现、IDEAgent 的质量与多样性记录、MAP-Elites 的空白区域探索、SenseNova 的证据管理、Solution Tournament／ARIS 的验证理念，以及 Agent4Sci 对“过早陷入微调”和“评测取巧”的实证研究。对应的原始论文与代码见 [方法来源](references/methods.md)。本 Skill 使用宿主原生多 Agent 功能，不包含或依赖这些项目的代码。
