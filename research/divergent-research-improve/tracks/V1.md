## 2. 三问 gate 的原文执行（L12）

1. 交付物是一个完整答案？是（换/不换 + 迁移面）。
2. 现在就能说出至少两个原理不同的做法？是（换库 / 不换但锁 PEM+algorithms / 自写 30 行 HMAC 校验）。

## 3. 判别问题与实测（这是唯一真的会失败的检查）

派发前写（RUN.md）：
- P1 若把依赖树压到"离线安装、无编译扩展"，两库可安装性会怎样？（施加：删掉 wheelhouse 里的 cryptography 与 gcc）
- P2 若用同一份畸形 token 喂两库 decode，接受/拒绝怎样？（施加：同一输入）
- P3 若只允许 GHSA + PyPI + 官方文档，近 24 个月响应差异能否判开？（施加：换信息来源）

结果：
- **P2 我的预测翻了**：我以为"python-jose 接受、PyJWT 拒绝"。实测（probe_p2.out，python-jose 3.5.0 / PyJWT 2.15.1）：DER 公钥冒充 HMAC secret 时**两库都 ACCEPT**（PyJWT 在显式 algorithms=['HS256'] 下）；PEM 版本两库都 REJECT；PyJWT 不传 algorithms 直接报错。→ 真正的判别线不是"库安不安全"，而是"应用层只喂 PEM/SPKI + 锁 algorithms"。**这条实测把两路从"不同机制"合并成一条**，正是 L56 想要的效果，且成本只有 20 行脚本。
- P3 判得开：一边有未修 critical，一边 2026 年内 6 次发布。
- P1 未施加（只有 requires_dist 元数据：python-jose 拖 ecdsa/rsa/pyasn1，PyJWT 核心零依赖），我按"只见到元数据"处理，没写"已验证"。

一手锚点（GHSA-3qf3-8w2g-rqmx，2026-09-03 发布，2026-10-05 更新）：
> "python-jose through 3.5.0 fails to properly validate asymmetric keys in HMAC initialization, accepting DER-encoded public keys that lack PEM armor or SSH prefixes."

配 `vulnerabilities[0] = {"vulnerable_version_range": "<= 3.5.0", "first_patched_version": null}` → 截至今天**无补丁**。我的前验"3.4.0/3.5.0 已在 2025 恢复发版 → 风险解除"被推翻，这是先想后搜带来的唯一实质收益（我原本会直接说"还在维护，不用换"）。
