## 我在文本里看到的可检验缺陷

1. **顺序自相矛盾**：§1 先说"先花少量搜索确认领域版图"，再说"避免被第一批热门方案锁定"。先搜后想正是锚定的来源。视角应在检索前由问题结构生成，检索只用于查漏。
2. **"原理不同"没有判据**：`mechanism_key` 由汇总者事后命名，换名即"新机制"。缺一个反事实判据（去掉某组件后哪个方案仍成立）。
3. **独立性无证据**：要求 tracks 分开存，但没有派发原文、时间戳、Agent 事前预期。无法区分"真隔离"与"主 Agent 把结论喂进去"。
4. **空搜索不可见**：只要求记录"找到的资料"，不要求记录"搜过但没找到"。缺口分析因此只能凭印象。
5. **停止条件主观**："新增可行机制很少"没有操作定义；也没有按边际信息量分配下一轮预算的规则。
6. **预算与并行冲突**：quick 3 路 + "用户要求并行至少 3 路"；若用户既要 quick 又要不并行，两条规则打架。
7. **60 分钟自查是装饰**：SKILL.md 自己承认宿主可能没有定时能力，却仍以时间为主触发条件；experiment-protocol 的事件触发写法更好。
8. **checker 可被绕过**：
   - `pass` 只要 `artifact` 非空字符串（写 "TBD" 也过）；
   - 一族只要**任一**候选有 checked primary 证据就算"已取证"；
   - 方向"覆盖"只看是否被引用，不看该候选是否只是换名；
   - `criterion` 为空只是 warning。
9. **缺"选择"的形式**：没有要求成对支配比较或"什么证据会让我改选"，容易退化成加权总分。
10. **quick 档对小问题过重**：3 个 Agent + 证据 + 验证，对"查一个事实"是流程税。

## 我的候选机制（待与各路对比，不预设采纳）

- H1 视角前置 + 覆盖轴登记（先写轴，再检索）
- H2 差异见证（counterfactual witness）替代事后命名
- H3 每路事前登记：预期、计划查询、可推翻条件、时间盒
- H4 负结果日志（搜过什么、没找到什么）
- H5 无子 Agent 时的降级协议（顺序角色 + 明确标注独立性未验证）
- H6 边际新机制族 = 0 时停止；预算按信息量再分配
- H7 选择用硬约束 → 成对支配 → 翻转条件，而非加权总分
- H8 审查者盲评 + 必须给可证伪的具体反对意见
- H9 checker 增加 witness/axis/负结果/pass 证据形态校验
- H10 quick 档减负（2 路或 1 路 + 交叉领域扫一遍）
